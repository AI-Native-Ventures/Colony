## Visual contract

- Retain Colony's far-left community rail, workspace sidebar, central channel and adjacent right-hand thread. Do not introduce a website dashboard or separate task application.
- Preserve the approved spacing, rounded surfaces, original wordmark and ants, accent-responsive channel/thread surfaces, and mesh/diagonal/halo background treatments.
- Use production Inter message typography, with 14px regular message text, readable line spacing, compact metadata and generous separation between contributions. Keep the website's creative typography distinct from Colony's message typography.
- Agents have a consistent name, role below the name, Agent identity and assigned colour. The Website Manager leads; research, designer-builder and independent review agents execute their respective work.
- Each channel entry is a thread root. The right panel displays the same job and replies. It must not create a second task, disconnected conversation or duplicate approval.

## Required experience

### Brief

The owner supplies the existing website and asks for an improved design in ordinary language. The root contains the source reference and an inline website job block. The manager confirms what will be preserved and what will be redesigned. The job promises a website preview, desktop/mobile review and an explanation of improvements.

### Working

The root block shows source review, design/build, independent QA and owner review as named stages. Progress derives from actual work state. Worker findings appear in the same thread with roles and colours. The manager coordinates the work and brings back reviewed artifacts.

Use Horizon's Build Website Studio Method: deep factual crawl, one fused designer-builder with creative freedom, independent visual/functional review, then a reviewable preview. Preserve a strong original's identity while elevating it; reimagine a weak design from the business material. Reconcile stale supporting skills and weak existing gates when adapting the method.

### Review

- Render a substantial inline website preview in the job block, not just a URL or tiny attachment.
- Provide Before/Redesign selection, desktop/mobile preview, expanded inspection and a visible version.
- Compare captured original content against the actual generated redesign; never substitute the illustrative websites from this concept for user work.
- Include independent QA details and the manager's concise account of the improvements.
- Keep Request changes and Approve design in the thread as shown.
- A revision request triggers real delegated work, produces a new preview/version, preserves previous versions and returns to review. It must not merely modify the displayed headline or simulate an agent reply.

### Handover

- Design approval leads to the approved version, source/assets, review record and launch preparation.
- Keep design approval separate from publication. Approval of a preview does not authorize a silent production cutover.
- Identify any domain/hosting access needed and prepare an owner-reviewable handover request in the same job.
- Retain the approved version for later changes, a new review cycle and recovery.

## What belongs only to the concept

The Brief/Working/Review/Handover selector outside the app is a demonstration control. Do not ship it as a control that fabricates job progress. The concept's example identities, source comparison, progress, QA result and responses are illustrative. Production must bind the same experience to real agents, artifacts, permissions and durable state.

The approved inline blocks are reusable presentation capabilities authored/populated by agents. Do not hard-code Horizon Labs, sample website copy or this example's outputs into production.

## Completion gates

1. Compare the rendered application with this exact approved reference at matching desktop widths for Brief, Working, Review, Revision and Handover. Verify the community rail, right thread, typography, spacing, tinted surfaces and substantial inline previews.
2. Exercise the real website job from source URL through crawl, design/build, independent review, preview and owner revision. Demonstrate an improved rendered site, not only code or passing tests.
3. Verify that approval references the reviewed version; revising invalidates stale approval. Confirm handover cannot silently publish.
4. Restart during work and after review; recover the same job, progress, artifacts and version without duplicate work or cross-community leakage.
5. Use GitHub CI for builds and automated checks as requested. CI, merge and publication are separate from rendered visual and functional acceptance.

Do not mark the Website Manager complete based on a smaller subset of these states. If a material change to the approved experience becomes necessary, show the concrete difference to the owner before treating that alternative as accepted.
