Agent Org and Visibility

Design spec · 2026-08-21 · Colony desktop, relay, ACP harness

Seven gaps that share one shape: the relay enforces a rule, the CLI can set it, and the desktop app shows nothing. This spec closes all seven in four shipping phases.

1. The problem

Colony already models an agent hierarchy. AgentTier (worker, leader, executive) is defined in crates/buzz-core/src/interrupt.rs:110, enforced at ingest in crates/buzz-relay/src/interrupt_gate.rs, and carried on two records: the managed-agent head (kind 30177, tier field in content JSON) and the employee head (kind 30190, rank tag, parsed in crates/buzz-core/src/employee.rs:80).

None of it is operable from the desktop app. Rank is fixed at creation via buzz employees hire --rank. There is no picker, no promotion path, no chart. v0.10.22 shipped read-only rank badges, which made the gap visible without closing it.

Auditing for the same pattern found six more instances. All seven are in scope.

2. Phase 1: make the working indicator tell the truth

Ships first because the app is currently displaying wrong information every day. Estimated 2 days. No relay changes.

2.1 Per-agent elapsed time (bug #7)

ActiveChannelTurnSummary carries a single anchorAt per channel, set to the earliest live turn across all agents in that channel (desktop/src/features/agents/activeAgentTurnsStore.ts:67). WorkingAgentRows computes elapsed once from that value and passes the same string into every row (desktop/src/features/sidebar/ui/ChannelActivityPopover.tsx:199).

Two agents that started 40 seconds apart therefore display identical elapsed times, both reporting the older one's duration.

The per-agent data is already correct upstream. The store tracks startedAt per turn and applies a per-agent clock-skew offset, and its own documentation states that distinct agent starts yield distinct anchors. The collapse happens only in the channel-level aggregate.

Change

export type ActiveChannelTurnSummary = {
  channelId: string;
  anchorAt: number;          // kept: earliest, drives the sidebar's single badge
  agentCount: number;
  agentPubkeys: string[];
  agentNames?: string[];
  agentAnchorsAt: number[];  // NEW: per-agent, index-aligned with agentPubkeys
};
  • anchorAt stays as-is. The collapsed sidebar badge (8s (2)) is correctly the channel's oldest live turn.
  • agentAnchorsAt[i] is agent i's own earliest live turn in this channel, skew-corrected the same way anchorAt already is.
  • WorkingAgentRows computes formatElapsed(now - agentAnchorsAt[index]) per row.
  • Alignment failure (length mismatch) falls back to anchorAt, matching the existing alignedAgentNames guard rather than rendering blank.

Tests

  • Unit, in activeAgentTurnsStore.test.mjs: two agents, starts 40s apart, one channel. Assert two distinct anchors, and that anchorAt equals the minimum.
  • Unit: an agent with two live turns in one channel anchors to its earliest.
  • Unit: array length invariant holds for pubkeys, names, and anchors together.
  • Run each against the unfixed store first and confirm it fails.

2.2 Agents that look idle while working (bug #8)

This one gets a probe before it gets a fix. The obvious hypothesis is already disproven, and shipping against the wrong cause here means tuning a timeout that hides the symptom.

What is already ruled out

The badge requires a liveness frame and prunes a turn after roughly 25 seconds of silence (LIVENESS_INTERVAL_MS and REMOVE_AFTER_MS, activeAgentTurnsStore.ts:16-22). The natural guess is that a long native subagent call blocks the harness from emitting.

It does not. run_turn_liveness is spawned as an independent tokio task at turn_started and pinned for the whole turn (crates/buzz-acp/src/pool.rs:1706), with a default interval of 10 seconds. A blocked tool call does not stop it. The comment there records that this was deliberate: session creation and context fetches can each outlast the desktop's prune window.

The two remaining candidates

  1. Work happening outside any ACP turn. Liveness is per-turn. If the agent's CLI finishes its ACP turn and then keeps working, through a native subagent it spawned, a background poll, or a scheduled job, there is no open turn to emit liveness for. The badge correctly reports "no turn in flight" while the machine is genuinely busy. This is a modeling gap, not a timing bug.
  2. Native subagents that emit no observer frames. When a CLI harness spawns its own child agents, those children are invisible to the observer stream. The parent turn stays live and the badge survives, but the activity headline goes quiet, which reads as stalled.

The probe (first task of the phase, roughly 1 hour)

  1. Run a live agent through a task that spawns a native subagent and takes over 60 seconds.
  2. Capture the observer frame stream for that agent, timestamped.
  3. Answer three questions with evidence, not inference:
    • Does turn_completed arrive before the work actually finishes?
    • Do turn_liveness frames continue at 10s across the blocked span?
    • Do any frames describe the subagent's work?

Candidate 1 points at the harness: the turn must stay open, or a distinct background-work signal must exist. Candidate 2 points at the transcript: the badge is right and the headline needs a fallback such as "working, no detail reported". The fix is designed after the probe reports, not before.

Explicitly out of scope: raising REMOVE_AFTER_MS. Both candidate causes survive a longer timeout, so that change would only lengthen the window in which a genuinely dead agent still looks alive.

3. Phase 2: People and Roles

Closes gaps #1, #2 and #5. Estimated 4 days. Relay changes required.

3.1 The data change: one new field

Every agent gets an optional manager: a single 64-character hex pubkey.

  • Managed agent (kind 30177): "manager": "<hex>" in the content JSON.
  • Employee (kind 30190): a manager tag on the head, sourced from the hire request.
  • Executives have no manager. Absence is the root marker, not a sentinel value.
  • Workers and leaders may have none. They render in an Unassigned tray. Nothing breaks and no migration is required.

3.2 Relay validation

Added alongside the existing tier checks in interrupt_gate.rs:

  1. If manager is present, the manager's tier must equal filer_tier.escalation_target() exactly. Worker to leader, leader to executive. Anything else is rejected at ingest.
  2. The manager must have a resolvable head in the same community.
  3. An executive carrying a manager is rejected. There is no rank above it.
  4. A manager pointing at the agent itself is rejected.
  5. Tier in 30177 content is trusted only when the head is signed by an owner. Today the tier resolver falls through to the content tier field when no employee row exists (interrupt_gate.rs:236), so a self-published head can name its own rank. Closing that is part of this phase.

Cycles are impossible by construction: the tier ladder is a strict total order and every edge climbs exactly one rung. No cycle detection is needed, and none should be written, because a cycle check would mask a broken tier rule rather than surface it.

3.3 Setting rank: two paths, two mechanisms

Managed agents

The head is owner-authored, so a tier or manager change is a republish of kind 30177 with new values. No new event kind.

Employees: new kind 9046, employee update

The employee head is signed by a relay-held key, so the owner cannot edit it directly, and re-running hire would mint a second keypair for the same role, losing the identity, its memory, and its history.

Kind 9046 is an owner-signed request carrying the employee pubkey plus the new rank and/or manager. The relay verifies the signer is a current owner, applies the same validation as above, and republishes the employee head at 30190. Identity, role slug, and keypair are untouched.

Registered in crates/buzz-core/src/kind.rs, parsed in crates/buzz-core/src/employee.rs beside the existing hire request, handled in crates/buzz-relay/src/employee_broker.rs.

3.4 Lifecycle rules

EventRuleWhy
Manager is deleted or retired Reject the delete while it has reports. The error names them. The owner reassigns first. Silent reparenting moves authority without the owner deciding it.
An agent is demoted below its reports' escalation target Reject, naming the reports that would become invalid. Same reasoning. Fail loudly rather than orphan quietly.
An agent is promoted while it has open asks Open asks keep their original audience. Only new asks use the new line. Re-targeting a live ask changes who is accountable for a decision mid-flight.
Manager is not running Allowed. The org chart shows liveness on the node. The relay already files stall asks. The chart must not imply a dead team is healthy.

3.5 Ask routing

buzz asks raise --to keeps requiring an explicit audience, and the relay keeps enforcing the one-rank-up rule. What changes is the default: when the filer has a manager and --to is omitted, the ask addresses that manager. An explicit --to still wins, still validated.

This is the whole point of the phase. Escalation stops being a lottery among everyone at the next rank.

3.6 Desktop: the People and Roles screen

A new top-level section under Agents, with three parts.

Org chart

  • Agents only. Humans are never drawn: the owner sits above the entire structure and can address any agent directly, so placing them in the tree would misrepresent both facts.
  • Executives are roots. Multiple executives means multiple roots, drawn side by side.
  • Each node shows: avatar, name, tier badge, live or idle state, and the count of active grants (the grant detail itself lands in phase 3).
  • An Unassigned tray below the tree holds workers and leaders with no manager.
  • Drag to reassign is explicitly deferred. Reassignment is done through the edit dialog.

Role editing

  • Tier picker and manager picker on the agent edit dialogs (AgentDefinitionDialog, AgentInstanceEditDialog).
  • The manager list only contains agents exactly one rank up, so an invalid edge cannot be composed in the first place. The relay still validates: the UI narrows, it does not authorize.
  • Rejections surface the relay's own message. No client-side paraphrase.

Hiring

  • Hire an employee: role slug, display name, rank, optional manager. Publishes kind 9045.
  • The head arrives asynchronously (the relay mints the keypair), so the row shows a pending state until 30190 lands, rather than a spinner with no explanation.
  • Promote and demote through kind 9046.
  • KIND_EMPLOYEE, KIND_HIRE_REQUEST and KIND_EMPLOYEE_UPDATE added to desktop/src/shared/constants/kinds.ts.

3.7 Tests

  • Rust ingest tests per rejection rule, following the existing crates/buzz-relay/tests/interrupt_gate.rs pattern: wrong-tier manager, cross-community manager, executive with manager, self-manager, self-declared tier on an unsigned head.
  • Rust: kind 9046 from a non-owner is rejected; from an owner it republishes the head with the same pubkey and role.
  • Rust: deleting a manager with reports is rejected and the error names them.
  • Desktop unit tests for the tree builder: multiple roots, orphans, a manager pointing at a deleted agent, and an agent whose manager is in the Unassigned tray.
  • Playwright screenshot of the org chart with a populated tree and a non-empty tray.

4. Phase 3: Authority

Closes gap #3 and the coupling hole. Estimated 3 days.

Tier answers "who may I interrupt". A delegation grant answers "what may I decide". They were built separately and nothing joins them, so a worker can escalate correctly to its assigned leader and that leader can be equally unable to decide. The tree routes perfectly and the work still stalls, while the chart shows a healthy structure.

Grants are kind 30189, created by buzz grants create with a category, a precise scope, and an optional cap in nanoUSD (crates/buzz-cli/src/lib.rs:3097). Wildcards are refused. Hard-list categories (spend, external_send, hiring, legal, pricing, deletion, vendor) are refused outright and always go to the owner. Revoking republishes the head with active=false; the record is never deleted.

Scope

  • KIND_DELEGATION_GRANT added to kinds.ts.
  • A grants surface: every grant, its holder, category, scope, cap, and active state.
  • Create and revoke from the app. The owner key signs, exactly as the CLI does.
  • Grants shown on the agent's org chart node and in its profile, so authority and rank are read in one place.
  • A warning on the chart when an agent has reports but no grants: it can receive escalations and decide nothing.

Client-side validation mirrors the relay's refusals (no wildcard scope, no hard-list category) so the owner is told why before signing, but the relay remains the authority.

5. Phase 4: Accountability

Closes gaps #4 and #6. Estimated 2 days.

5.1 The decision log is written and never read

A leader deciding under a grant logs it at kind 44303: the grant cited, the tasks covered, the category, what was decided, the money moved, and an undo path. The undo path is mandatory, on the stated principle that no undo path means no autonomy (crates/buzz-cli/src/lib.rs:3151). The relay checks the category matches the grant and the cap holds.

The kind is absent from the desktop app. Add it, and a reverse-chronological view filterable by agent, grant, and category, reachable from an agent's profile and from the org chart node. The undo path is rendered as the primary content of each row, since it is the only field the owner acts on.

5.2 Asks that answer themselves

An ask can carry a default option and a time window. The relay computes a deadline at file time and applies the default when the window expires (crates/buzz-relay/src/ask_broker.rs:137-151). When the ask does not set its own window, a community-wide default fills in. Hard-list categories may never carry a default, so the worst cases are already protected. Everything else is not.

AskDetailCard shows no countdown. A decision can be made by the owner's silence on a surface that never mentioned a clock was running. Add:

  • A live countdown and the exact option that will apply on expiry.
  • Escalating visual weight as the deadline nears.
  • The same countdown wherever asks are summarized, not only in the detail card.

6. What this deliberately does not do

  • It does not put anyone between the owner and an agent. Direct messaging is unchanged. The thread exemption in crates/buzz-relay/src/interrupt_gate.rs:378 already lets an agent reply to a thread the owner started or was pulled into, and the manager is not copied on it.
  • It does not route work downward. Nothing is auto-delegated. The chart makes the upward path specific; it does not assign tasks.
  • It does not add capacity limits. A leader with twenty workers is visible and permitted. Making that visible is the point; policing it is a later decision with real evidence behind it.
  • It does not add a handoff view. When a worker escalates out of the owner's thread, the ask carries its origin thread and the answer returns correctly, but the manager must open the ask to see context. Worth doing, worth seeing whether it bites first.

7. Sequencing and acceptance

PhaseDaysPasses when
1. Working indicator2 Two agents started 40s apart in one channel show different elapsed times in a live app, and the probe has produced a written finding naming the cause of the idle-looking badge.
2. People and Roles4 An agent is promoted from worker to leader in the app, given a manager, appears correctly in the chart, and its next ask reaches that manager by default with no --to.
3. Authority3 A grant is created and revoked in the app, and the chart shows which agents can decide and which cannot.
4. Accountability2 A logged decision is readable with its undo path, and an ask with a window shows a live countdown naming the option that will apply.

Roughly 11 days. Each phase ships independently and is proven in the running app, not in tests alone. Phase 1 goes first because it is cheap and the app is currently showing wrong numbers.

8. Open questions

  1. Kind number 9046 for the employee update is provisional. Confirm it is free when the phase 2 work starts.
  2. The probe in 2.2 may reclassify bug #8 as a harness change rather than a desktop one. If it lands in the harness, phase 1 grows by roughly a day.
  3. Whether the Unassigned tray should be a soft warning or a hard blocker on agent creation. Recommendation: warning only, so an agent can be created before its manager exists.
