Role Agents

One agent identity per workspace role, runnable on any member's device, with attribution intact. Design agreed 2026-08-04.

Problem

Today each install mints its own agents: keys in the local keychain, processes on the local machine, billed to that machine's subscription. When a second member joins a community, their app provisions its own starter team, so the workspace ends up with two Chiefs of Staff that share nothing: separate identities, separate memory, separate DM threads. For a company workspace this is wrong. "Chief of Staff" should be one colleague everyone talks to.

This is upstream Buzz working as designed: Buzz binds every agent to exactly one human owner (NIP-OA auth tag), because attribution is its core promise: who instructed the agent, and whose agent did the work. Colony diverges deliberately, and the design below keeps both attribution guarantees while merging the entity.

The model

Rule 1: the requester's device executes.

Every member's machine runs the role agent with the shared key, filtered to respond only to that machine's own user. Your message wakes your copy; your co-founder's wakes theirs. No leader election, no duplicate replies, and the asker is by definition online, so the agent never looks dead because someone closed a laptop.

Rule 2: attribution moves from ownership to operation.

Who instructed the agent is already provable: prompts are signed human messages. Who did the work becomes an operator tag on every agent event, naming the member whose device executed that turn. The relay admits the role key on the strength of member-level auth (multiple owner tags or a team-level tag) instead of a single owner's NIP-OA tag. Both of Buzz's attribution promises survive; the entity merges.

Rule 3: work products live on the relay, not the laptop.

Chat memory is already shared through the relay. Work memory is not: a file drafted on one machine is invisible to the other, and "continue where you left off" breaks exactly when continuity matters. Workspace agents therefore write to relay-hosted git and Blocks; local disk is scratch space. This is also simply good collaboration hygiene for the humans.

Rule 4: privileged agents stay pinned.

An agent holding deploy keys or production credentials keeps the shared identity but executes on exactly one designated host. "Runs anywhere" is for thinking work, not for credentials. And personal agents remain a legitimate separate category: per-user, private, clearly labeled, never auto-shared by joining a workspace.

Billing

Requester-pays falls out of Rule 1 for free: each turn runs on the asking member's device with that member's LLM credentials. The cost ledger records spend per operator, so the workspace sees who spent what through one agent, rather than every member funding a private clone.

Rollout

  1. Stopgap, config only: open respond_to on the existing fleet plus join-flow dedup. One fleet, owner-hosted. Kills the duplicate-colleague problem this week at the cost of host-online and host-pays.
  2. Role identity: key sync, requester-executes filter, operator tags, member-level admission. The full model above.
  3. Relay-resident work: agents route work products through relay git and Blocks so continuity holds across devices.
  4. Optional, later: cloud-hosted execution for roles that want perfect consistency and workspace billing. The identity and attribution layers from phase 2 carry over unchanged; only the execution host moves.

Risks and open questions

  • Key distribution is the crown jewel. A role key on N devices is N chances to leak it. Pairing must be explicit, per-device, revocable, and rotation on member removal is not optional.
  • Environment divergence. The same agent with different tools installed behaves differently per device. Phase 3 narrows this; role manifests (declared tool expectations) could narrow it further.
  • Presence flapping. Two harnesses setting presence for one identity need a shared-presence convention (online if any device is online).
  • Buzz upstream drift. This is a protocol extension in our fork. Upstream merges touching NIP-OA or the harness owner logic will need care.
