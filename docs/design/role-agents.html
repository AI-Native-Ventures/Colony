Role Agents

A workspace role is one colleague in the UI and one owned instance per member underneath. Revised 2026-08-05.

Revision. The first version of this design shared one agent keypair across member devices. That is superseded: sharing a private key across machines created the worst risk in the document (distribution, and rotation whenever a member leaves) to buy an illusion the presentation layer can provide for free. The model below keeps per-member owned instances - which is what Buzz already does safely - and merges them into one entity where it matters: in the UI.

Problem

Agents are per-install: keys in the local keychain, processes on the local machine, billed to that machine's subscription. When a second member joins a community, their app provisions its own starter team, and the workspace shows two Chiefs of Staff. For a company workspace that is wrong. "Chief of Staff" should read as one colleague.

Two things were conflated in that complaint, and separating them is the whole design:

  • Execution should be per-member: my request runs on my Mac, on my subscription, with my files; yours runs on yours. This is correct already and worth preserving.
  • Presentation should be per-role: one name, one member-list row, one mention target. This is what is broken.

The model

Rule 1: one instance per member, owned by that member.

Every member who needs a role runs their own instance with their own keypair, created from the same persona and stamped with the same role identifier. Instances stay respond_to: owner-only. Your message is answered by your instance on your machine with your credentials; your co-founder's by theirs. Requester-executes and requester-pays are not features to build - they are what per-member ownership already does.

Rule 2: the UI presents a role, not its instances.

Anywhere agents are enumerated - member lists, mention autocomplete, huddle participants, channel pickers - instances sharing a role identifier collapse into one entry, named for the role. Actions on that entry resolve to the viewer's own instance. The Agents management screen is the deliberate exception: it manages processes, so it shows what actually runs on this machine.

Rule 3: attribution needs no new mechanism.

The superseded design had to invent operator tags because one key served many people. Here each instance is bound to exactly one owner by its NIP-OA auth tag, exactly as upstream Buzz intends. Who instructed the agent is a signed message; whose agent did the work is the owner tag. Both guarantees hold with zero protocol change - which is the strongest argument for this model.

Rule 4: work products live on the relay, not the laptop.

Chat history is shared through the relay, so the role's channel memory converges: every instance reads the same channel. Local disk does not converge. Workspace agents therefore put work products in relay-hosted git and Blocks, so "continue what we discussed" resolves for whichever member picks it up. Private DM history with a role is per-member and stays that way - that is a feature, not a gap.

Rule 5: some roles stay single-instance.

A role holding deploy keys or production credentials should exist once, on one designated machine, and be reachable by members through an explicit allowlist rather than cloned per member. Personal agents remain a separate category entirely: per-user, private, never merged into a workspace role by joining.

Rollout

  1. Phase 1 (shipped 0.10.7): join-flow dedup so a joiner does not mint a second unrelated team, plus member-wide respond_to as a stopgap so a joiner is not agent-less. Both are superseded by phase 2 and the respond_to half is reverted by it.
  2. Phase 2: the model above - persisted role identifier, joiner mints its own instance of each role, role-merged presentation, owner-only restored, presence union.
  3. Phase 3: agents route work products through relay git and Blocks, so role continuity holds across members.
  4. Later: cloud-hosted instances for roles that must answer when nobody's laptop is open. The role identifier and merged presentation carry over unchanged; only the execution host moves.

Risks and open questions

  • A role is only as consistent as its personas. Two members' instances can drift (different harness, model, or system prompt). The role identifier lets us detect divergence; whether to enforce convergence is open.
  • Mid-channel handoff. If one member asks a role to start something and another asks it to continue, continuity depends on Rule 4 having been followed. Until phase 3, expect gaps for filesystem work.
  • Cost visibility. Requester-pays is right, but the workspace should still be able to see role-level spend across members. The cost ledger records per-instance today; a role-level roll-up is a reporting question, not an architectural one.
  • Onboarding cost. Every joiner now provisions instances, so joining is heavier than joining a chat app. Mitigation: provision the lead role only, and let further roles be created on demand.
