Getting the price right per provider, in real time

Design note, 2026-08-05. Why the ledger should never chase live prices, and what it does instead. Grounded in what the meter already records and what was verified against OpenRouter and vendor pricing pages this week.

The problem, stated precisely

The same model is served by many providers: the lab itself, Google Vertex, AWS Bedrock, Alibaba, DigitalOcean, aggregators like OpenRouter, and local runtimes that cost nothing. Prices differ per provider and change, sometimes permanently, sometimes for a window. Verified this week: deepseek-v4-flash is sold by 21 providers at $0.084 to $0.14 per MTok, a 67% spread on one model string.

Today the price book keys on model name alone. A call served by DigitalOcean gets priced at DeepSeek's direct rate. The usage record already knows who served the call, the pricing function just never looks.

The trap in the question. "How do we get the price in real time" assumes the price must be right at the moment of the call. It does not. The ledger prices records at read time (engine.rs, price_tokens(model, tokens, at_unix)), not at capture time. What must be right in real time is the facts: who served it, which model string, how many tokens of each kind, when, at what tier. Facts are immutable. Prices are a lookup that can be corrected after the fact, and the correction retroactively fixes every affected record. Telecom has billed this way for fifty years: capture the call detail record at the switch, rate it against a tariff table, re-rate when the tariff was wrong.

Three layers of price truth

Ordered strongest first. Each layer covers the failure of the one below it.

Layer 1 Observed cost: the provider states the invoice line itself

Some routes report the exact cost of the call in the response. OpenRouter returns usage.cost when asked, and its generation endpoint exposes the native cost per request. When the wire carries a cost, the meter records it as a fact: observedCostNanousd on the usage record. The engine uses it over any book row, because no table lookup beats the seller's own line item.

This dissolves the aggregator problem. The 21-provider spread on deepseek-v4-flash lives almost entirely inside routers like OpenRouter, which dynamically pick the upstream per call. No book can key on a choice made per request, but the router invoices per call, so we take its number. Reconciliation still checks the aggregate against the router's billing, so a lying router is caught at layer 3.

Layer 2 The signed book, with provider as a first-class dimension

For direct calls (Anthropic, OpenAI, DeepSeek, Vertex, Bedrock, Alibaba) no per-call cost comes over the wire, so the book prices them. One addition: provider joins the conditions system that already handles tier, token bounds, and daily windows.

  • CallFacts gains provider, read straight off the record.
  • PriceConditions gains provider: Option<String>. Most-specific-wins already exists: a (deepseek-v4-flash, provider: alibaba) row beats the bare deepseek-v4-flash row for Alibaba calls and touches nothing else. Provider gets the largest specificity weight, above tier: it is an identity dimension, not a discount dimension.
  • Bare rows keep their current meaning, the vendor-direct list price, so every existing book and all 433 production records price identically after the change. That invariant gets its own test, same discipline as the per-MTok migration.
  • Catalog merge and dedupe keys already serialize conditions, so provider rows flow through merge_catalogs and the signed feed unchanged.

Layer 3 Reconciliation: aggregate ground truth

The engine already sums metered spend per provider-day, which is exactly the shape a vendor invoice has. Anthropic and OpenAI admin APIs report actual billed cost; a mismatch beyond tolerance flags the provider-day and a correction event (kind 30186) restates it. This is the backstop that catches whatever layers 1 and 2 got wrong, including a price change nobody noticed. Blocked today on the two admin keys.

Who is the provider? One rule

The provider is whoever invoices you, not whoever made the model. Claude served through Vertex is vertex, because Google bills it and Google's price applies. A model served through OpenRouter is openrouter, whichever of its 21 upstreams did the work, because OpenRouter's charge is the cost. This one rule decides every ambiguous case, and it is the only definition under which reconciliation against invoices can ever balance.

The meter normalizes the wire's base URL to a canonical slug at capture time: anthropic, openai, deepseek, openrouter, vertex, bedrock, alibaba, local. Slugs are part of the record contract, documented next to the catalog.

Local models: priced at zero, never defaulted to zero

Local runtimes (Ollama, LM Studio) get explicit all-zero catalog rows for provider: local. The distinction matters:

StateMeaningSpend screen
priced $0We know this call was freeCounts, costs nothing
unpricedWe do not know what it costFlagged for review

Nothing is ever assumed free. An unknown provider is unpriced and visible, not zero and invisible.

Why not a live price API at call time

ReasonDetail
AuditabilityA ledger must reproduce any charge later. "We asked an API at that moment" is not reproducible. A signed, effective-dated book is: the same facts against the same book give the same nanoUSD forever.
The APIs are wrongVerified this week: OpenRouter's catalog lists deepseek-v4-flash cache read at $0.028/MTok; DeepSeek's own page says $0.0028. Ten times off. Auto-ingesting that feed would have silently poisoned the book. A human signs every change; automation only proposes.
CouplingPricing must not die when a third-party API does, and most providers offer no per-call quote endpoint anyway.

All the machinery already shipped. The feed is the delivery channel; this design only widens what a row can say.

Visible basis, the last honesty guarantee

Every priced line records which layer and which row priced it: observed, book row (model, provider), or book row (model) fallback. A fallback-priced line on a model the watchdog knows has provider spread is a visible prompt to add the row. Wrong prices hide; a stated basis cannot.
