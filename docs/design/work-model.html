The Work Model

Threads are where work is discussed. Tasks are what work is. Two levels of work, never three. Chains are flat siblings, not nested children. Everything you can group by is a real domain field, never a label someone typed.

Examples throughout are a website agency because that is the business in hand. The primitives are not. Section 3c runs the same model against a recruitment firm and a social agency, names the four places it was leaking sales vocabulary, and names the one shape it still does not cover.

01 The model

Three nouns. One of them is not work.

Grouping · not work

Cohort

A named set of Parties. @premium-q3. Built by lead discovery or by hand. Mentionable. Has no status, does nothing on its own.

Recipe · not work

Pipeline template

Ordered stages. Each stage declares owning team, channel, doer kind, reviewer, prompt, cost ceiling. @build-websites. Versioned.

Work

Initiative → Task

Cohort × template, fired, produces one Initiative and a flat set of Tasks. This is the only thing that has status, cost, and a neck to blame.

That chain repeats once per party, all sharing one initiative_id and their own subject. Three stages × 38 parties = 114 tasks. Flat. No nesting anywhere.

Why no third level. Every task system that allows subtasks eventually answers "how deep?" with "however deep somebody clicked." Rollup percentages stop meaning anything, boards cannot render, and cost double-counts because every level charges a cost centre. Depth here is bought, not free: a task that turns out to be a project escalates into a child Initiative, which costs an approval and shows up on the board as an event.

02 Canon

Ten rules. Each one is a decision that closes an argument.

R1 Two levels of work. Never three.

Initiative groups Tasks. Task has no children. Ever.

Depth arrives only through escalation (R9), which is gated and visible.

R2 A Task is one deliverable.

Something is one task if and only if: exactly one team can be blamed, it has a single definition-of-done, and it lives in one channel. Break any one → split it.

This is the test that settles "is QA a task?" and "is this two things?"

R3 Review is a gate, not a task.

A reviewer is a second agent on the same deliverable. inProgress → inReview → completed. Accountability never moves off the owning team.

Splitting review into its own task creates two necks for one outcome, which means none.

R4 Task points at thread. Thread never points back.

Task carries thread_root. A thread's task list is a query, never a tag on the thread root event.

A tag would have to be rewritten every time the active task changes: signed-event edits, LWW conflicts, lost history. A query gives you full history free and ordered.

R5 Two truths, never one badge.

Business state (status) and execution state (runStatus) disagree constantly and both are correct. Every card shows a status pill and a live dot.

Collapse them and you get cards reading "in progress" whose agent died 40 minutes ago. The dot going grey is the dead-chain detector.

R6 No custom fields. No free-text labels.

If you want to group by something and no field exists, that is a missing domain concept. Add the concept.

Labels cannot drive automation, so chains would depend on humans typing strings correctly. This is the single rule that keeps this from becoming Jira.

R7 Eager tasks, lazy threads.

Fan-out writes the whole graph immediately, downstream tasks blocked. Threads are created only when a task becomes ready.

You see 114 tasks of committed work before it costs money, and a crashed agent cannot silently delete the rest of the pipeline. Channels stay clean because dead threads never appear.

R8 Rejection is a bounce, not a new task.

A downstream task bounces upstream with a reason: upstream returns to ready with the reason attached, downstream returns to blocked. Bounce count is a quality metric.

Cancel-and-recreate destroys the link between the complaint and the work, which is the only data that tells you which agent produces garbage.

R9 Depth is bought with an approval.

A task too big for one deliverable spawns a child Initiative (spawned_from_task_id). Parent task sits blocked until it completes.

Escalation, not recursion. One hop, cost-estimated, owner-approved, visible.

R10 Templates are pinned at fire time.

An Initiative records the template version it ran. Editing a template never mutates a run in flight.

Otherwise a typo fix silently changes what 38 leads are getting halfway through.

R11 The agent writes its own contract.

An agent starting ambient work fills in the whole brief — title, description, inputs, acceptance, expected outputs — and updates it when scope changes. Every task gets a real title, including the throwaway ones.

The agent knows what it is doing better than any heuristic. Fan-out gets its contract from the template stage instead; both paths produce the same record. Nothing is ever hidden — the implicit flag is a filter, not a verdict.

R12 A task must survive being handed to a stranger.

A pooled agent claims it having never seen the thread. Everything needed is on the task, typed and resolvable, or the task is broken.

This is the test that forces inputs, acceptance and declared outputs to exist. A title and a sentence fail it instantly, and they fail it silently — you get bad work, not an error.

3b The task contract

The test a task has to pass: a pooled agent claims it having never seen the thread. Everything it needs is on the task or the task is broken. A title and a sentence fail that test instantly.

1 · Brief
title — ≤60 chars, the deliverable
description — one sentence, the done-condition
instruction — what to actually do. From the template stage, interpolated with the subject. Bounded (the job queue already caps instructions at 8,000 chars).
2 · Inputs

inputs: [{role, kind, ref, required}] — typed references, never prose. kind reuses the artifact union: event · url · path · text, plus party and task-artifact.

The edge I missed. depends_on is ordering only — it carries no payload. The outreach writer needs the built site URL, and ordering does not hand it over. So a chain has two edges: depends_on for sequence, and an input of kind task-artifact pointing at the upstream task's output for data. Templates wire the second one per stage.
3 · Acceptance

acceptance: [{id, text}] — a short checkable list, not a paragraph. The reviewer grades against these. A bounce names a failed criterion id, not free text.

Turns "the pack was wrong" into "criterion industry-fit failed, 6 times this week, always from writer-2". Free-text reasons never aggregate.
4 · Outputs, declared before work starts

expects: [{kind, format, label, cardinality}] — the same union as artifacts, declared up front. "One url labelled staging site" · "One text in markdown, ≤2,000 chars".

This one is enforceable today. The relay already refuses a task-linked done outcome with no artifacts (job.rs:583) and already fences event artifacts to the exact channel, thread, job, task and attempt (job_broker.rs:554). Adding "and it must match what the task declared" extends a check that exists rather than inventing one.
5 · Constraints
cost_ceiling — hard stop for this task
due_at / staleness_after — hours for an agent, days for a person
tool_scope / permission_mode — what the doer may touch
6 · Delivered

artifacts: [TaskArtifact] — already exists (taskRunContracts.ts:39), with a primary-deliverable distinction already rendered in TaskDetailSheet.tsx.

Declared and delivered are the same shape, so the detail sheet shows them as two columns and a missing output is visible before anyone reviews anything.

Same contract, six renderings

A task is not a page. It is a record that renders differently depending on who is looking and why. The last row is the one people forget.

SurfaceShowsDeliberately hides
Board card title · subject · status pill · run dot · blocked-by count · missing-output warning everything else. Eight words, scannable at 114 cards.
List row the above plus team, assignee, age, bounce count instruction, inputs, acceptance
Thread chip title · status · dotall of it — the thread is the conversation, not the record
Task detail sheet the whole contract: inputs as resolvable links, instruction, acceptance as a checklist, expected vs delivered side by side, constraints, bounce history nothing. This is the one place the full record lives.
Human queue card description, and inputs rendered as content — the site opened, the pack readable, the phone number tappable — plus outcome buttons acceptance criteria, tool scope, cost ceiling, refs-as-refs. She needs the material, not the spec.
Agent prompt the contract serialised to text: instruction, resolved inputs, acceptance criteria, declared outputs, cost ceiling board metadata, history, anything it cannot act on
The prompt is a surface. A task that renders beautifully in the sheet and vaguely in the prompt is a broken task, and it fails invisibly — you get bad work rather than an error. Every field added to this contract has to answer "how does this serialise into the brief the agent actually reads".

One shape difference that needed a new mechanism

A website run is 1 : 1 — one lead, one chain, count known before firing. Recruitment is 1 : N and the N is discovered mid-run: sourcing one role produces 40 candidates, and each needs its own screen chain that nobody could have planned for.

A stage marked fan_out turns its declared outputs into the subjects of a child run. That is R9's escalation path, automated: still one hop, still budget drawn from the parent, still visible as an event on the board. Two levels of work survive intact — what grew is the number of runs, not the depth of a task.

One shape this model does not cover yet, stated plainly. A social agency's work is recurring — the same five stages, every account, every month, forever. Nothing here schedules a run. Everything is fired by a person or an agent saying so. Retainer and account-management work is also not a run at all: it has no end, so "initiative completed" never happens and a board built around finishing has nothing to show. That is a real gap, not a detail, and it wants a recurring-run concept (template + cohort + schedule) that this document does not attempt. Better to name it than to pretend the fan-out covers it.

04 Lifecycle

One state machine for business truth, one for execution truth. They are not the same machine.

Business state CompanyTask.status

blocked → ready — every depends_on completed
ready → inProgress — claimed by a member of the owning team
inProgress → inReview — doer submits, reviewer_team set
inReview → completed — reviewer accepts
inReview → inProgress — reviewer rejects, same task, same neck
any → snoozed — wake_at set, returns automatically
downstream ⇢ upstream ready — bounce, carries a reason (R8)
any → cancelled — owner or cascade
Today completion is only reachable through review. company.rs:396 permits no Ready→Completed and no InProgress→Completed: every task must pass inReview, and qa_persona_id is a required String, not an option. That is correct for agent work and wrong for Sarah — nobody reviews a phone call. Ruling: InProgress→Completed is permitted when doer_kind: human and the stage declares no reviewer. Agent tasks keep the mandatory gate.

Execution state TaskRunHead.runStatus

Already exists. Driven by the job broker's lease + heartbeat. Nobody sets it by hand.

queued — filed, no worker has claimed it
executing — lease held (120s), heartbeat every 30s
recoverable — lease lapsed, attempts remain (max 3)
delivered — outcome accepted with evidence
failed — worker reported failure
abandoned — lapsed on the last attempt, never re-offered

Exact values from taskRunContracts.ts:7 and job.rs:326. The parser refuses any head whose job status and run-status disagree, so the two truths can differ but never contradict.

Human tasks have no lease. A person does not heartbeat, and rerouting their work to someone else is not allowed anyway. Instead a staleness clock: inProgress with no activity for N days raises an Ask to the owner. Nudge, never reroute.

Free funnel data. Forcing a reason on human completion is not bureaucracy — it is the only place conversion data can come from. "40 completed" is worthless; "18 sent, 9 replied, 3 booked, 10 disqualified" is the business.

4b How a task finds a doer

A stage names a team, not a persona, so several agents are eligible for every task. Nobody assigns. The relay pushes awareness; the agent pushes commitment.

Machines claim

Because they are interchangeable and can prove liveness with a heartbeat. Racing is correct here.

People are assigned

doer_kind: human → direct assignment, no lease, no CAS. Sarah does not race for work and cannot heartbeat. Staleness clock instead.

Why the relay does not assign. To assign well it would need to know which agents are alive, free and capable. It knows none of them: presence says connected, not able, and the real constraint — free ACP slots against parallelism — lives in the desktop process where the relay cannot see it. Assign to a sleeping laptop and the task is orphaned until some timeout, so you add a timeout, a reclaim, and a lease — and you have rebuilt claiming with worse information, plus a second source of truth that can disagree with the lease.

The only new code

A local delay function. Inputs: warm session for this subject, free slots against parallelism, cost tier against the task's ceiling, recent bounce rate on this stage. Capability is a hard filter, never a delay.

Best fit waits least. CAS stays the sole arbiter, so no new consistency problem is introduced — ties simply degrade to a plain race.
Claim storms

38 tasks go ready at once and every agent sees all 38. Unshaped, they all fight over task 1, then task 2, then task 3.

Each agent walks its queue in an order shuffled by its own pubkey. They spread with zero coordination and no shared state.

07 Loopholes, and the ruling on each

Every one of these is a way the model gets gamed, silently rots, or lies to you.

HoleWhat goes wrongRuling
Cap evasion by escalation
bigger than it looks		 Agent hits its grant cap, spawns a child Initiative, child kicks off tasks, spending continues. And today there is nothing to evade: the grant cap is checked per decision, with no running total, no grant balance, and no link at all to the cost ledger (interrupt_gate.rs:778). Budgets are reporting-only — BudgetStatus has no path back into filing, claiming, or running a job (ledger/engine.rs:172). Nothing stops spend anywhere. Cap becomes cumulative over an initiative tree: a child initiative draws from the parent's remaining budget and cannot mint its own. Requires new machinery — a spend total joined to the initiative via AgentWorkContext, and a pre-claim check. Treat this as its own phase, not a field.
Implicit task flood
not a loophole		 Every thread mints a task for cost attribution, so chat volume lands on the board. Not a problem to solve, a filter to provide. Every task is created, boarded, and countable. Board and list default to implicit = false — genuinely assigned work. One toggle shows everything, and "everything" is the honest view of what your company actually spent its turns on. Hiding rows, classifying them as chores, or gating on turn counts were all ways of deciding for the reader what counts as work. The reader decides, per view.
Duplicate work Same party sits in two cohorts. Two initiatives each build a site. Two sites, double spend, client gets two emails. Fan-out planner checks for an open task with the same (subject, stage) anywhere in the company. Collisions are surfaced in the approval Ask as a skip-list, defaulting to skip.
Accountability laundering An agent from another team claims a task, so the failure lands on a team that never took the work. Claim gate checks membership of owning_team_id. Also inherits the relay's existing hard rule: only the job's own human may claim it — no cross-seat rerouting, ever.
Human task rots forever
half built		 Sarah goes on leave. Twelve leads sit inProgress and nobody notices for a month. The stall sweep already exists (interrupt_runtime.rs:1326) and fires on any in-progress task with no event activity for BUZZ_STALL_AFTER_SECS, default 6 hours. A human task has no event activity by nature, so today it would page you every six hours, forever. Staleness threshold becomes per stage, set by the template — hours for an agent, days for a person. The existing sweep, dedupe key, and Ask plumbing are reused as-is. This is a parameter, not a system.
"Completed" means nothing Board says 40 completed. Twelve of them were closed to clear the queue. Human completion requires an outcome_reason. There is no bare "done" button.
Template drift mid-run Template edited on Tuesday; leads 1–20 got one thing, 21–38 get another, nothing records it. Version pinned on the Initiative at fire time (R10). Editing offers "apply to future runs only".
Board cannot filter at all Multi-letter tags are silently dropped by the nostr filter type. team, cost-centre and initiative are already on task heads and already unfilterable — a client asking for one run gets every task in the company. Single-letter mirrors, same pattern the relay already uses for c ↔ company (company_broker.rs:105). Needed for the three that exist plus every new dimension. Cheap now; a data migration once there are runs in flight.
Runaway fan-out A mention resolves to 4,000 parties and starts 12,000 tasks before anyone reads the message. Fan-out always plans first, then raises a cost Ask with count and estimate. Auto-approval only under an explicit grant, and only below its cap. Planning is free; creating is gated.
Cancel leaves spend running Owner kills a campaign; agents mid-turn keep burning tokens and publish work into dead tasks. Cancel is a two-phase cascade: unstarted tasks → cancelled immediately; in-flight ones get a stop signal and are marked cancelling until their turn ends. Board reports both counts.
Naming collision — worse, it is taken "Campaign" is already a Colony concept: Discovery campaigns are lead-acquisition runs with their own id, plan and cap, stored in private Postgres (discovery_workspace.rs:53). If a group of leads is also called a campaign, two different objects share one word and the one people mean is the one that does not exist yet. User-facing words: Cohort (who), Template (how), Run (this time). Campaign stays Discovery's. "Initiative" stays the internal kind name and is never shown.
Outcomes die on the task Sarah disqualifies a lead. The task closes. The lead still reads Qualified, so the next cohort picks it up again and pays to build another site. outcome_reason writes through to PartyRelationship.status, which already has exactly the right five values (party.rs:190): Candidate, Accepted, Qualified, Disqualified, Dormant. Disqualify → Disqualified. Snooze → Dormant. The task records what happened; the relationship records what is now true about the lead.
Thread context bleed ACP sessions are keyed by channel. 38 leads in one channel share sessions — the agent mixes Ridgeway's brand into Kalahari's site and it looks like model error. Session key becomes (channel, thread_root). Already decided. This gates fan-out — without it, the whole design produces confidently wrong work.

08 Build order

Each phase is usable on its own. Nothing here needs the phase after it to be worth shipping.

Phase 0 · gate

Thread-scoped agent sessions

Session key (channel, thread_root), affinity and eviction updated. Blocks everything else — fan-out into one channel is unsafe until this lands.

Phase 1 · schema

Edges and index

depends_on, subject, stage, thread_root, doer_kind, snoozed, outcome_reason. Relay emits indexed tags. Blocked-state derivation on the relay.

Phase 2 · see it

Work surfaces

Board (stage columns), list with group/sort/filter, thread task chip + history, deep links both directions. This is the phase that pays for itself — it works on today's tasks before any fan-out exists.

Phase 3 · doers

Human queue + bounce

Queue view, outcome reasons, bounce transition, staleness clock → Ask. Makes the last mile of the chain real instead of a card nobody opens.

Phase 4 · targets

Cohorts + entity mentions

Cohort kind, typed mentions so @premium-q3 and @build-websites resolve to something other than a person. Composer, ingest, and agent prompt context.

Phase 5 · the ask you started with

Templates + fan-out

Template kind, planner, dedupe check, cost estimate, approval Ask, eager graph write. The sentence "@mark take the leads from @premium-q3 and use @build-websites" works here and not before.

Order is deliberate. Phase 2 ships value against work you already have. Phases 4 and 5 are the flashy part and they are last, because a fan-out you cannot see, cannot stop, and cannot trust the output of is worse than no fan-out.
